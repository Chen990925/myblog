# 微服务 1：架构与服务拆分/通信方式

## 一、项目架构与服务拆分

**10 个服务**：api-gateway（网关）/ main（业务公共）/ orderservice（指令+风控+审批）/ tradeservice（交易核心）/ tradegatewayfrontend（报盘前置：CFETS/CSTP/TradeWeb）/ unify-access×4（算法接入/AMS/文件报表/IR 三方接入）/ scheduler-center（调度）/ user-center（用户+SSO）

**拆分维度**：
- 按业务能力：指令 → 审批 → 交易 → 报盘（业务流水线）
- 公共能力下沉 common：缓存（common-cache）、额度引擎（avail-engine）、费率（trade-fee-engine）、数据同步（data-sync）

**拆分原则（话术）**：高内聚低耦合 + 单一职责 + 数据私有（每服务自己的表）；代价：分布式事务、链路复杂、运维成本。

## 二、通信方式（项目两种并存，重点）

| 方式 | 项目用法 | 选择逻辑 |
|---|---|---|
| **同步 Feign**（109 客户端） | 查询类、强依赖结果（查额度/风控/基础数据） | 要立刻拿到结果 |
| **异步 MQ**（RocketMQ） | 下单请求→报盘前置、成交回报、清算（REQ/PUSH 成对） | 解耦 + 削峰 + 不依赖同步返回 |

**话术**："同步用 Feign、异步用 MQ：下单请求发 MQ 到报盘前置（前置吞吐低要削峰、不能因前置慢拖死主链路）；查额度/风控这种要立刻拿结果的走 Feign。"

## 三、服务通信的坑（引出后续块）

1. 同步调用链路过长 → 延迟叠加、故障传导（雪崩）
2. Feign 超时配置不当（**项目 readTimeout=600s**）→ 线程长占
3. 无熔断降级 → 单点故障放大

## 四、面试话术（1 分钟版）

> "项目 10 个服务：网关、业务公共、指令、交易、报盘前置、四个接入服务、调度、用户中心；按业务能力拆分、公共能力下沉 common 模块。服务间两种通信：查额度/风控这类要立刻拿结果的走 Feign 同步（109 个客户端）；下单到报盘、成交回报走 RocketMQ 异步（解耦削峰，前置挂不影响主链路）。架构代价是分布式事务和链路复杂度——我们用 MQ 最终一致 + 状态机替代强事务。"

## 五、高频追问

- 为什么拆这么多服务？→ 按业务边界 + 独立部署（交易高峰期可单独扩容交易服务）；代价是复杂度
- 服务边界怎么定？→ 业务能力 + 数据归属（每服务私有表）；避免共享数据库
- 什么时候用同步、什么时候异步？→ 要立刻拿结果用同步；削峰/解耦/长耗时用异步
- 分布式事务怎么处理？→ 最终一致（MQ 消息 + 本地表补偿/事务消息 + 幂等），不强求 2PC
