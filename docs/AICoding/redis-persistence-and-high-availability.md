# Redis 4：持久化 + 高可用

## 一、为什么需要持久化

Redis 是内存数据库，重启/宕机数据丢失。缓存可回源 DB，但**锁/计数/会话**等关键数据丢了会出问题 → 需要持久化兜底。

## 二、RDB（快照）

- 触发：save/bgsave、配置 `save 900 1` 等
- `bgsave`：**fork 子进程**写 RDB 文件，**COW 写时复制**（fork 后父子共享内存页，父进程修改的页复制，子进程看到 fork 时刻的一致快照）
- 文件 dump.rdb（二进制紧凑、恢复快）
- ✅ 恢复快、文件紧凑、适合备份；❌ **丢失窗口大**（两次快照间全丢）、fork 有短暂阻塞
- 面试点：RDB 是"某一时刻完整快照"，fork+COW 保证一致性；`save` 同步阻塞，生产用 `bgsave`

## 三、AOF（命令日志）

- 每次写命令追加到 AOF 文件，重启重放命令恢复

**三种刷盘策略（背熟）**：
| 策略 | 行为 | 可靠性 | 性能 |
|---|---|---|---|
| appendfsync always | 每条 fsync | 最多丢 1 条 | 最慢 |
| appendfsync everysec | 每秒 fsync | 最多丢 1 秒 | 折中（**生产默认**） |
| appendfsync no | 交给 OS | 丢最多 | 最快 |

- **AOF 重写（rewrite）**：文件无限增长 → `bgrewriteaof` 重写为最小命令集（100 次 incr → set key 100），同样 fork+子进程
- ✅ 数据可靠；❌ 文件大、恢复慢（重放命令）

## 四、RDB vs AOF 对比

| 维度 | RDB | AOF |
|---|---|---|
| 文件 | 小紧凑 | 大（命令日志） |
| 恢复 | 快 | 慢（重放） |
| 丢失窗口 | 分钟级 | everysec 最多 1 秒 |
| 写性能 | 影响小（fork 子进程） | everysec 有磁盘 IO |
| 适用 | 备份/容忍丢失 | 可靠性要求高 |

**生产推荐（4.0+）**：**RDB + AOF 混合**（aof-use-rdb-preamble yes，AOF rewrite 时以 RDB 为 base）——兼顾恢复快 + 丢数据少。
话术："缓存数据用 RDB（快、能容忍丢失）；业务关键数据用 AOF everysec（最多丢 1 秒）；生产 RDB+AOF 混合。我们系统参数/行情是缓存性质（丢了回源 DB 重建），锁/幂等要 AOF 保障。"

## 五、高可用三层

### 1. 主从复制（Replication）
- 主写从读（读写分离）；复制流程：从发 psync → 主 bgsave 生成 RDB 传给从 → 从加载 → 主把期间写命令放 repl_backlog → 从追增量 → 实时命令传播
- **问题**：主挂从不自动升级（需人工/哨兵）；复制异步（主从不一致——分布式锁丢失的根源）

### 2. 哨兵（Sentinel）自动故障转移
- 监控主从，主挂自动把从升主（failover）
- 机制：哨兵集群（≥3 奇数）→ **主观下线（sdown）**（单哨兵超时）→ **客观下线（odown）**（多数确认）→ leader 选举 → failover（选从升主，其他从指向新主）
- 客户端连哨兵拿新主地址
- 面试点：哨兵解决高可用（自动转移），但异步复制仍可能丢数据；哨兵自身要集群

### 3. Cluster（集群）分布式扩展
- **16384 个 hash slot**：`key → CRC16(key) % 16384` → 分配到节点
- smart client 按 slot 路由；算错节点返回 **MOVED 重定向** 让客户端跳转
- 每个分片主从（主挂从顶上）
- 限制：跨 slot 多 key 操作不支持（除非 **hash tag** `{user:1}:name` 保证同 slot）
- 面试点：集群解决扩展性+高可用（分片+分片内主从）；哨兵=单机高可用、集群=多机分片

### 架构对比（背熟）

| 架构 | 解决 | 容量 | 分片 | 故障转移 |
|---|---|---|---|---|
| 单机 | 基础 | 单机 | 无 | 无 |
| 主从 | 读扩展/备份 | 单机 | 无 | 手动 |
| 主从+哨兵 | 高可用 | 单机 | 无 | 自动 |
| Cluster | 扩展+高可用 | 多机 | 16384 slot | 自动 |

## 六、数据丢失场景（深挖，呼应分布式锁）

1. **异步复制丢写**：主收到写命令但未同步给从 → 主挂 → 新主缺这部分数据
2. **脑裂（split brain）**：主网络分区，哨兵选新主，旧主恢复后继续写（客户端还连旧主）→ 旧主数据孤立丢失；`min-replicas-to-write`（从节点数量不足拒绝写）缓解
3. 所以 **Redis 锁不能保证强一致**（RedLock 背景）

## 七、面试话术（1 分钟版）

> "持久化两种：RDB 全量快照（fork+COW，恢复快、丢数据多），AOF 命令日志（everysec 最多丢 1 秒、恢复慢），生产 RDB+AOF 混合。高可用三层：主从解决读扩展和备份（异步复制、主挂需人工）；哨兵解决自动故障转移（sdown/odown、leader 选举、从升主），哨兵要奇数集群；Cluster 解决水平扩展（16384 slot 分片、CRC16 路由、MOVED 重定向、分片内主从）。架构代价是异步复制丢数据、可能脑裂——所以分布式锁强一致诉求靠业务幂等兜底，或直接上 ZK。"

## 八、高频追问

- bgsave 会阻塞？→ fork 瞬间阻塞（页表复制），fork 后子进程写磁盘不阻塞主进程
- everysec 丢多少？→ 最多 1 秒写命令
- 哨兵怎么选主？→ 从节点按配置优先级/复制偏移量/runid 综合；需多数哨兵同意（客观下线）
- 为什么 16384 slot？→ 权衡：太多心跳大、太少迁移粒度粗（512 节点内够用）
- MGET 跨 slot？→ hash tag {key} 保证同 slot；或客户端拆分
- 主从复制全量还是增量？→ 首次/断链太久全量（RDB），运行中增量（repl_backlog）
