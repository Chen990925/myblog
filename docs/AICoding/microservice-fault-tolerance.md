# 微服务 5：容错治理（熔断/降级/隔离）——含诚实校准

## 一、雪崩与三个保护手段

| 手段 | 作用 | 触发 |
|---|---|---|
| **熔断** | 快速失败，避免继续调用故障依赖 | 失败率/慢调用比例超阈值 |
| **降级** | 兜底（缓存/默认值/友好提示） | 熔断触发或异常时 |
| **隔离** | 防单个依赖占满所有资源 | 线程池/信号量隔离 |

**雪崩链路**：外部依赖变慢 → 调用线程阻塞 → 线程池耗尽 → 服务不可用 → 上游也超时 → 全链路瘫痪

## 二、Sentinel 核心概念

- **资源**：被保护的调用点（方法/接口）
- **规则**：流控（QPS/线程数）/ 熔断降级（慢调用比例/异常比例/异常数）/ 热点参数 / 系统自适应
- **滑动窗口统计**：LeapArray 时间窗统计 QPS/RT/异常
- **熔断状态机**：Closed（正常）→ Open（熔断快速失败）→ Half-Open（探测放少量请求）→ Closed/Open
- 对比：Hystrix（线程池隔离、已停更）vs Resilience4j（函数式、轻量）

## 三、⚠️ 项目诚实校准（面试必须说清）

```
事实：项目 pom 无 Sentinel/Hystrix/Resilience4j 依赖；yml 里的 sentinel 是 Redis 哨兵；
     代码无 @SentinelResource/BlockHandler/Fallback —— 即没有熔断降级实现

正确话术：
"我们目前只有超时控制，没有熔断降级——这是已知短板：Feign readTimeout 600s + 无熔断，
外部系统变慢会耗尽线程池（我们确实遇到过 CFETS 变慢导致连锁变慢）。改进方案：
① 收紧超时（连接 3s/读 10s 分级）；② 引入 Sentinel 失败率熔断 + 快速失败；
③ 关键外部调用信号量隔离；④ 回报链路改 MQ 异步化（这个已做）。"
```
**价值**：坦诚 + 有分析 + 有方案，体现工程判断；编造"用了 Sentinel"会被追问细节打死。

## 四、隔离方式对比

| 方式 | 特点 | 适用 |
|---|---|---|
| 线程池隔离 | 独立线程池，调用与业务线程解耦；有切换开销 | 强依赖、耗时操作 |
| 信号量隔离 | 只限并发数不占额外线程，轻量 | 快速失败、内部调用 |

## 五、限流（网关层，项目未实现）

- 算法：计数器 / 滑动窗口 / 漏桶 / 令牌桶
- 实现：Sentinel 流控 / Redis 令牌桶（Gateway RedisRateLimiter）/ Nginx limit_req
- 项目落点："网关可按 func_id/租户限流（Redis 令牌桶），防单客户打满"

## 六、面试话术（1 分钟版）

> "容错三层：熔断快速失败、降级兜底、隔离防占满。我了解 Sentinel 的滑动窗口统计和 Closed/Open/Half-Open 状态机。坦白说我们只做了超时（配置还偏松 600s），没做熔断降级——我分析并提过改进方案：收紧超时 + Sentinel 熔断 + 信号量隔离；回报链路已经用 MQ 异步化解耦。雪崩的根因是线程被慢依赖占满，所以核心是'限时 + 限流 + 限并发'。"

## 七、高频追问

- 熔断和降级区别？→ 熔断是"断开调用"（保护自己），降级是"提供兜底"（保护用户体验）；通常熔断后走降级
- 熔断阈值怎么定？→ 失败率（如 50%）+ 最小请求数 + 统计窗口；慢调用比例（如 RT > 1s 占比 50%）
- 为什么 Hystrix 被替代？→ 停更、线程池隔离开销大；Resilience4j/Sentinel 更轻量灵活
- 线程池隔离和信号量隔离怎么选？→ 强依赖/耗时用线程池隔离（不阻塞业务线程）；快速失败/高频内部调用用信号量
- 项目怎么防雪崩？→ 现状只有超时（不够）；方案：收紧超时 + 熔断 + 隔离 + 异步化（MQ 已做）
