# MQ 2：生产端可靠发送（生产端确认）

## 一、三种发送方式

| 方式 | 行为 | 可靠性 | 适用 |
|---|---|---|---|
| 同步 syncSend | 发送后阻塞等 SendResult | 最高 | 关键消息、需要立刻知道结果 |
| 异步 asyncSend | 回调确认（SendCallback） | 高 | **高频、不想阻塞（项目用）** |
| 单向 sendOneWay | 只发不管 | 最低 | 日志/监控/可容忍丢失 |

**SendResult 四种状态（背熟）**：
```
SEND_OK                    正常（已写入 Broker）
FLUSH_DISK_TIMEOUT         写入内存但刷盘超时（可能没落盘）
FLUSH_SLAVE_TIMEOUT        主写成功但从没同步
SLAVE_NOT_AVAILABLE        主写成功但从不可用
```
- **只有 SEND_OK 才算真正可靠**；后三种当"半成功"处理（消息可能丢）
- 项目落点：onSuccess 没检查 SendStatus——FLUSH_DISK_TIMEOUT 也是风险（可讲）

## 二、发送失败重试（第二层）

- 同步/异步默认各重试 2 次（`retryTimesWhenSendFailed`/`retryTimesWhenSendAsyncFailed`）
- 解决：瞬时网络抖动、Broker 短暂不可用

## 三、本地补偿表（第三层，可靠消息经典方案）

```
问题：业务操作与消息发送无法原子（先发消息再提交事务→事务回滚消息已发；先提交再发→发失败丢）
方案：
① 业务事务内：写业务数据 + 写本地消息表（同事务）→ 原子
② 事务提交后：异步发送消息，成功后标记"已发送"
③ 定时任务：扫"未发送/超时未确认"记录 → 重发（业务幂等保证重复无害）
```
- 最终一致：不追求同时成功，保证"业务成功 → 消息最终一定发出"

项目落点："下单 asyncSend onException 只记日志丢消息无补偿——改进：下单事务写本地消息表 + 定时补偿重发。"

## 四、事务消息（RocketMQ 原生版）

```
① 半消息：发送消息（对消费者不可见）→ 执行本地事务
② 本地事务成功 → commit（消费者可见）；失败 → rollback（丢弃）
③ 半消息超时未确认 → Broker 回查（check）本地事务状态 → 决定 commit/rollback
```
- 关键：**回查（check）机制**——Broker 不知道本地事务结果，靠回调查询；回查接口要幂等
- 对比本地表：事务消息原生少代码；但只支持单 Broker 组内
- 项目落点："下单这种'业务+消息'一致性要求高的场景，可评估事务消息替代本地补偿表。"

## 五、消息结构（小点）

- Message：topic + tag + key + body + 属性
- **key 用业务唯一键（订单号）**：按 key 查询排查（mqadmin queryMsgByKey）+ 影响路由（同 key 同队列）
- 项目落点："消息没显式设 key，排查单条链路不方便，建议 key 用订单号。"

## 六、面试话术（1 分钟版）

> "生产端可靠性三层：第一层发送确认——三种方式只是确认时机不同，SendResult 四种状态只有 SEND_OK 算真成功，FLUSH_DISK_TIMEOUT 半成功要警惕；第二层发送重试——默认 2 次解决瞬时抖动；第三层本地补偿表——业务事务写消息表+定时重发最终一致。更优是事务消息（半消息+本地事务+Broker 回查）。我们下单走 asyncSend，onException 目前只记日志，正在评估补本地消息表或事务消息。"

## 七、高频追问

- 同步异步怎么选？→ 关键要立刻知道成败用同步；高频不想阻塞用异步；可容忍丢用单向
- SendResult 后三种要不要处理？→ 要，当半成功：FLUSH_DISK_TIMEOUT 可重试；SLAVE_NOT_AVAILABLE 看容忍度
- 本地表 vs 事务消息？→ 本地表应用层实现通用可控；事务消息原生少代码、依赖 MQ 特性
- 回查失败会怎样？→ 消息保持半状态，最终超时丢弃或按回查结果处理
- 重试会导致重复发送？→ 会！消费端必须幂等（下一块前提）
- 发送成功但业务失败？→ 本地表方案业务和消息同事务，业务失败消息也不发；事务消息同理
