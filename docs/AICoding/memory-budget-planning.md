# 内存预算核算：新服务器 JVM 参数配置方法论

> 核心一句话：内存预算 = 确定性开销（算得死）+ 弹性开销（按业务优先级分）；先算死，再分配，最后用 GC 观测验证回收。
> 三步走：盘清楚机器有什么 → 算清楚每类开销怎么估 → 自上而下分配 + 自下而上验证，两向收敛。

## 1. 五步流程（新服务器 JVM 参数确定法）

### Step 0：摸机器
```bash
free -h          # 总内存（不含 swap）
nproc            # 8 核
df -h            # 500G 磁盘：规划日志/dump/备份
cat /proc/meminfo | grep -i 'MemTotal\|SwapTotal'
```
要点：OS 预留 + 页缓存一般按总内存 10% 算（32G 留 3G 左右），别把 32G 全分光。

### Step 1：进程级盘点——这台机器到底跑什么
所有 JVM 服务 + 所有中间件 + 监控 agent，每一样都占内存：
- JVM 服务：main / orderservice / tradeservice / algo / gateway / unify-access×4 / scheduler / user-center ≈10 个
- 中间件：Nacos、Redis、RocketMQ Broker、ZK、MySQL（或远端）
- 监控：monitor-sdk/exporter、Agent

### Step 2：算每类开销——JVM 内存"六大件"（背熟）

| 组成部分 | 怎么估 | 本项目现状 |
|---|---|---|
| 堆（-Xms/-Xmx） | 靠压测活跃集 ×(2~3)，见 Step 4 | 13.25g |
| Metaspace | 先给 256m，看 `jstat -gc` 的 M/MC 趋势再调 | 256m×10 |
| 线程栈 | 线程数 × Xss（最容易被忽略） | 1000 线程×512k≈512m/进程 |
| 直接内存 | 有 Netty/NIO（行情、FIX）才需要，默认 256m | 256m×10 |
| Code Cache | 默认上限约 240m | ≈2.4g |
| JVM 自身开销 | 编译器/JIT/GC 结构 100~200m/进程 | ≈1~2g |

关键算术：堆 3g 的服务 RSS ≈ 3g 堆 + 256m 元空间 + 线程栈 + 256m 直接内存 + 240m CodeCache ≈ 4.2~4.5g。32G 上 10 个服务"算着够、跑着超"，超卖经常超在非堆部分。

### Step 3：两向收敛——自上而下分配 vs 自下而上验证
- 自上而下：总内存 32G − OS/页缓存 3G − 中间件 6G = 23G 可给 JVM → 按业务重要性分配堆
- 自下而上：每个服务按活跃数据/流量估算堆需求，加总 → 看是否超 23G
- 收敛不了就砍：砍的顺序：非核心服务先降（user-center、file-report），核心三兄弟（main/order/trade）最后动

### Step 4：用 GC 目标反推堆大小（最显水平）
- 堆与停顿目标联动：交易系统开市高峰 GC 停顿目标（如 G1 `MaxGCPauseMillis=200`）定了，堆不宜过大（越大 Mixed GC 越久）
- 堆下限：老年代活跃集 × 2 + 缓冲。活跃集来源：无历史数据靠压测，有历史数据看 GC 日志老年代水位
- 口诀：堆太小 → Full GC 频繁；堆太大 → 停顿失控 + 浪费；32G 上尤其防"给多了"

### Step 5：验证闭环（两周内完成）
```bash
jstat -gcutil <pid> 1000   # 观察 E/S/O 水位和 FGC 频率
jmap -histo:live <pid>     # 确认活跃集，校核 Step 4 估算
```
开盘高峰压测 → 看 GC 日志是否达成停顿目标 → RSS 是否超预算 → 调完再测。新服务器第一周目标不是"一次配对"，是"监控到位、能观测、敢调"。

## 2. 本项目完整推演（32G / 8 核 / 500G）

**确定性开销：**
- 中间件：Nacos 0.5g + Redis 2g（含页缓存）+ RocketMQ Broker 2g + ZK 0.5g + 监控 agent 0.5g ≈ 5.5g
- OS + 页缓存预留：3g
- 剩给 JVM：32 − 5.5 − 3 = 23.5g

**堆分配（按业务优先级）：**

| 服务 | 堆 | 理由 |
|---|---|---|
| main | 3g | 业务公共模块，交易全链路依赖 |
| orderservice | 3g | 指令/风控，核心 |
| tradeservice | 3g | 交易执行，核心 |
| algo | 1g | 算法接入，策略计算密集但并发有限 |
| scheduler | 1g | 定时任务为主 |
| api-gateway | 0.25g | 无状态转发，256m 够 |
| unify-access×4 | 0.5g×4 | 接入类，IO 型 |
| 堆合计 | ≈13.25g | |

**非堆每进程 ≈0.8~1g**（256m 元空间 + 栈 + 256m 直接内存 + 240m CodeCache），×10 ≈ 8.5~10g。

**验证**：13.25 + 10 + 5.5 + 3 ≈ 31.75g —— 贴着 32G 上限，几乎没有余量。
面试话术：当前配置是踩着红线排的，一旦线程数涨到千级或中间件扩容就 OOM/触发 swap，下一步调优动作是 Xss 从 1m 降到 512k 省栈空间 + 给非核心服务降配。

## 3. 新服务器无历史数据时的三个兜底手段

1. 对标：参考同规格旧环境/同行业配置，先给保守值（核心 3g、接入 0.5g 的行业常见分法）
2. 压测：开盘高峰流量回放，`jmap -histo:live` 拿真实活跃集
3. 可观测兜底：先把 GC 日志、jstat、监控告警建起来，用两周生产数据修正估算——"第一次配准"不是目标，"能观测、两周内调准"才是

## 4. 面试话术（背诵版）

> "新服务器我按三步走：先 `free -h`/`nproc` 摸清机器，预留 OS 和页缓存；再进程级盘点所有 JVM 和中间件，按'堆 + 元空间 + 线程栈 + 直接内存 + CodeCache'六项逐项核算 RSS；最后自上而下按业务优先级分配、自下而上用压测活跃集验证，两向收敛，超了就先降非核心服务。当前 32G 机器排 10 个微服务约 28~30G，贴着红线，所以我把 Xss 降到 512k、给缓存类服务控制线程数来挤出余量。"

## 5. 高频追问准备

- "Xss 512k 会不会栈溢出？" → 深递归/大栈帧方法（交易深调用链）才危险，正常业务 512k 支持几百层调用，用 jstack 观测线程栈深度验证
- "为什么 -Xms 要等于 -Xmx？" → 避免运行期堆扩容触发连续内存分配抖动，配合 AlwaysPreTouch 启动即稳定
- "8 核机器 Tomcat 配 1000 线程不是超卖吗？" → IO 密集场景线程主要是等外部（DB/外部接口），CPU 密集只有 8 个在跑；但 1000×512k=512m 的栈内存实打实 → 线程数 ↔ Xss 联动看
