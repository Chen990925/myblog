# MQ 3：Broker 存储与持久化

## 一、存储结构（三件套）

```
commitlog      顺序写所有消息（物理文件，默认 1G 滚动）——写入最快，磁盘顺序 IO
consumequeue   逻辑队列（每个 MessageQueue 一个），存 commitlog 的 offset 索引——消费定位
index          按 key 查消息的索引（可选）
```

**设计精髓**：
- 写入顺序 IO：所有消息只追加写 commitlog（单文件顺序写）→ 磁盘顺序写性能极高（高吞吐根基）
- 消费逻辑读：consumequeue 是逻辑队列，消费者按队列+offset 定位 commitlog 位置
- 对比 Kafka：Kafka 每分区独立文件；RocketMQ 所有队列共用一个 commitlog（顺序写更彻底）

## 二、刷盘策略

| 策略 | 行为 | 可靠性 | 性能 |
|---|---|---|---|
| 同步刷盘 SYNC_FLUSH | 落盘后才返回成功 | 高（宕机不丢） | 低（每次 fsync） |
| 异步刷盘 ASYNC_FLUSH | 写入 page cache 即返回，后台批量落盘 | 中（宕机丢毫秒级） | 高 |

项目落点："下单/成交关键消息应开同步刷盘；为吞吐用异步要能接受极端情况丢毫秒级数据。"

## 三、主从复制

| 策略 | 行为 | 可靠性 |
|---|---|---|
| 同步复制 SYNC_MASTER | 主写成功+从复制成功才返回 | 高（主挂从有数据） |
| 异步复制 ASYNC_MASTER | 主写成功即返回，从异步同步 | 中（主挂丢刚写数据） |

**可靠性矩阵（背熟）**：
| 刷盘 | 复制 | 等级 | 场景 |
|---|---|---|---|
| 同步刷盘 | 同步复制 | 最高（双保险） | 金融关键消息 |
| 同步刷盘 | 异步复制 | 高 | 一般关键 |
| 异步刷盘 | 异步复制 | 中（高吞吐） | 日志/可容忍丢失 |

## 四、消息不丢全链路（三层总纲）

```
生产端：重试（2 次）+ 本地补偿表/事务消息
Broker：同步刷盘（落盘才确认）+ 同步复制（主从双保险）
消费端：ACK 成功才确认 + 失败重试 + DLQ + 幂等
```

话术："消息不丢靠三层：生产重试+本地表补偿、Broker 同步刷盘+同步复制、消费端 ACK+重试+幂等。单层都可能丢，三层叠加才是可靠工程。交易关键消息用同步刷盘+同步复制最高配置。"

## 五、高频追问

- commitlog 满了？→ 滚动新文件；过期消息按保留时间清理（默认 72h）
- 消费 lag 存哪？→ 消费进度存在 Broker（offset）
- RocketMQ 为什么比 Kafka 适合交易？→ 可靠配置（同步刷盘）+ 事务消息 + 顺序消息成熟
- 同步刷盘性能？→ 每次 fsync 吞吐降几个量级；批量 + group commit 缓解
